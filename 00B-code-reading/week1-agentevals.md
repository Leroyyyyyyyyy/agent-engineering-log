### 动手前的检查清单

- [ ] 先在 issue 下留言认领(这个项目的惯例:说一声,等维护者回一句)
- [ ] 从 `upstream/main` 切新分支,不要在 `main` 上改
- [ ] **PR 必须带测试** —— CONTRIBUTING 原文:*Fix a bug — open a PR with a test that reproduces the issue*
- [ ] 测试要先复现 bug(不改代码时红),再证明修好(改完绿)
- [ ] commit message 用 conventional commits(仓库实际在用:`fix(log-enrichment): ...`、
      `test: ...`、`ci: ...`,scope 用模块名)
- [ ] 提交前跑 `make test-unit`,再跑 `make test`(`make test-integration` 要外部依赖,
      本地跑不动就在 PR 里说明)
- [ ] 仓库有 ruff 格式检查(见 commit `style: ruff format check`),提交前先格式化

### 立的规矩(00B 的第三条要求)

> **没逐行读过的生成代码不许提交。**

具体到这个 PR:如果用 AI 生成了共享 decoder 的实现,提交前必须能口头回答——
- 每个 `AnyValue` 分支为什么这么处理?
- 三个调用点原来的行为差异,改完之后是否**真的**统一了,还是只是看起来统一?
- 有没有哪个调用点原来的「有损」是**故意的**(比如为了输出体积)?

最后一条尤其重要。**issue 说「两个是有损的」,但没说那是不是 bug。**
提 PR 前先确认这一点,是这个 PR 里最值钱的判断。
