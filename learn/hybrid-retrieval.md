## 背景:两个公式

这一节是你需要的**外部知识**,不是要你抄的实现。

### BM25

给定查询 Q 和文档 D:

```
score(D, Q) = Σ  IDF(q) · f(q,D)·(k1+1) / ( f(q,D) + k1·(1 - b + b·|D|/avgdl) )
             q∈Q
```

- `f(q,D)`:词 q 在文档 D 里出现几次(词频 TF)
- `|D|`:文档长度(token 数);`avgdl`:全部文档的平均长度
- `IDF(q) = ln(1 + (N - n(q) + 0.5) / (n(q) + 0.5))`,`n(q)` 是含 q 的文档数

两个参数各控制什么 —— **这是必考点**:

| 参数 | 控制什么 | 极端值会怎样 |
|--|--|--|
| `k1` | 词频饱和速度 | `k1=0` 时词频完全不起作用,只剩 IDF |
| `b` | 文档长度归一化强度 | `b=0` 时完全不管长度,长文档天然占便宜 |

常用 `k1=1.5`、`b=0.75`。**用默认值就要说出来是默认值** —— 否则面试官会追问你是怎么调的。

### RRF(Reciprocal Rank Fusion)

```
score(d) = Σ  w_i / (k + rank_i(d))          k 通常取 60
           i
```

`rank_i(d)` 是文档 d 在第 i 个检索器结果里的**排名**(1 开始),没出现就不计这一项。

**为什么融合排名而不是分数**:余弦距离和 BM25 分数量纲完全不同,
要相加就得先归一化,而归一化方式本身会变成一个隐藏的调参旋钮 ——
**那个旋钮会悄悄替你做真正的决策**。用排名就绕开了这件事。

**代价**:RRF **奖励一致性**。两个检索器都找到的文档白拿一份加分,
只被一个检索器找到的文档会被系统性压制,**不管那个检索器多确信**。
记住这条,第三步会用到。

### 任务 A:代码感知分词器(约 30 行)

代码检索的分词和普通文本不一样。`FILE_TOOLS` 如果整体当一个 token,
查询里写 "tool groups" 就永远匹配不上;但只切成 `file`/`tools` 又丢了精确度。
**两个粒度都要留。**

验收(直接拿去跑):

```python
assert tokenize("class VectorStore:") == ["class", "vectorstore", "vector", "store"]
assert tokenize("FILE_TOOLS = [")     == ["file_tools", "file", "tools"]
assert tokenize("def embed_query(")   == ["def", "embed_query", "embed", "query"]
assert tokenize("向量检索默认返回几条结果") == []
```

最后一条**不是 bug,是设计**:纯中文切不出 ASCII token,所以 BM25 对中文查询贡献为零。
这一点后面会变成一个免费的对照组。

### 任务 B:BM25 索引(约 60 行)

一个类,构造时接收 `(ids, documents)`,提供 `search(query, n) -> [(doc_id, score)]`。

构造时要预计算:每篇文档的词频表、每篇长度、平均长度、每个词的文档频率。

**注意上面 IDF 公式里那个 `1 +` 是干什么的**:

经典 Robertson IDF 是 `ln((N - n + 0.5) / (n + 0.5))`,**没有 `1 +`**。
当一个词出现在超过一半文档里时,括号内小于 1,取对数就是**负数** ——
负分意味着「含有这个词反而扣分」,这通常不是你想要的。

加上 `1 +` 之后,下界变成 `ln(1) = 0`,**自然不会为负**。
自己验一下:把 `n = N`(所有文档都含这个词)代进去,等于多少?

> 我的 `hybrid.py` 里在平滑版之外还写了一层 `max(idf, 0.0)` —— **那是冗余的**,
> 用这个公式它永远不会触发。你重写时可以不写,但要说得出为什么不用写。

验收:

```python
# 213 篇文档,查一个明确的标识符,正确的块应该排第 1
hits = index.search("what is the value of BLOCKED_COMMANDS", 5)
# 中文查询应该返回空
assert index.search("向量检索默认返回几条结果", 5) == []
```

文档从哪来?**直接从 Chroma 取回**,不要重新调 `chunk_repository()`:

```python
collection = store.client.get_collection(collection_name)
got = collection.get(include=["documents", "metadatas"])
```

为什么:如果切块器改过而索引没重建,两条路会搜到**不同的语料**,
你就会得到一个无法归因的结果。**从索引里取,两个检索臂一定搜的是同一批文本。**

### 任务 C:RRF 融合(约 20 行)

输入两个 id 列表和两个权重,输出融合后的 id 列表。

验收 —— **这条测试比前面两个都重要**:

```python
# A 只被向量找到, 而且是 rank 1
# B 被两个检索器都找到, 但都只排 rank 10
vector_ids = ["A", "p1", "p2", "p3", "p4", "p5", "p6", "p7", "p8", "B"]
bm25_ids   = ["q1", "q2", "q3", "q4", "q5", "q6", "q7", "q8", "q9", "B"]

out = fuse(vector_ids, bm25_ids, 1.0, 1.0)

# A = 1/(60+1)              ≈ 0.0164
# B = 1/(60+10) + 1/(60+10) ≈ 0.0286
assert out[0] == "B"
```

**如果你的实现让 B 赢了,不是你写错了 —— 这就是 RRF 的设计。**
把这个数字算明白,你就懂了第三步为什么会翻车。

## 第三步:自己做实验(约 1.5 小时)

**这一步别看我的结论。** 顺序很重要:

### 3.1 先分开测两个臂 ← 从这里开始

在跑任何融合之前,先让 BM25 **单独**跑一遍评测,和纯向量对比,按类别列表。

```
类别                 向量单独    BM25单独
exact_identifier      ____%      ____%
semantic              ____%      ____%
value_lookup          ____%      ____%
cross_file            ____%      ____%
```

填完这张表再往下。**这五分钟的检查决定了后面要不要做融合。**

> **规则:如果一个臂在所有类别上都被另一个臂支配,融合不可能有增益,只能有稀释。**
> 融合的前提是**互补** —— A 在某类上赢 B,B 在另一类上赢 A。
> 没有互补就没有可融合的东西,**这时候调权重是在给噪声调音量**。
>
> 我把顺序做反了:直接实现融合就跑,一个类别掉了 36 个点,排查了一整轮才回头做这张表。

### 3.2 写预测,再跑参数扫描

**动手前先写下预测,四要素缺一不可:**

1. **方向** —— 数字往哪边动
2. **幅度** —— 大概多少
3. **作用范围** —— 哪些类别会动、**哪些不该动**(最容易漏的一项)
4. **机制** —— 为什么

作用范围这一项这次有个现成的**自检项**:中文 `semantic` 是纯自然语言,
BM25 切不出 token,**它在机制上就不该动**。如果它大幅变了,先查你的实现,别当成发现。

然后扫参数。建议 `CANDIDATE_K ∈ {10, 20, 50}` × `W_BM25 ∈ {0.3, 0.5, 1.0}`。

⚡ **效率提示**:别跑 9 次 `run_eval.py`。embedding 和 BM25 检索**只算一次**缓存起来,
换参数只是重新排序,几乎免费。9 组能在一次进程里跑完。

### 3.3 结果不对时,先分清是哪种「不对」

你大概率会看到某一类掉得特别狠。这时候要判断:

| 现象 | 更可能是 |
|--|--|
| 单一类别暴跌、其余不动 | **实现 bug 或参数错**,先查 |
| 各类别普遍小幅下降 | 方向问题 |

查的方法:**逐条列出正确块在「向量单独 / BM25单独 / 融合后」三处的排名**。
如果看到「向量 rank 1 → 融合后 rank 12」,回去看第二步任务 C 那个验收测试。

**参数问题和方向问题必须分开。** 参数错会让结果更差,但参数对了也救不回一个错的方向 ——
不区分的话,你会在错的方向上一直调下去。

## 面试怎么讲这一段

**别讲成「我做了混合检索」** —— 基础 RAG 已经是默认能力,当项目重点写是负资产。

要讲的是**判断链**:

> 我给检索系统建了 60 条分类评测集。上混合检索之前,我先把两个检索臂分开测了一遍 ——
> 发现 BM25 在四个类别上全都输给向量,而它唯一接近的那一类恰好是向量已经 100% 的。
> **没有互补性,融合只能稀释**,所以我没有继续调权重。
>
> 后来我还是跑了九组参数验证这个判断,没有一组赢过纯向量。
> 根因是词法鸿沟:自然语言用完整词,代码用缩写 ——
> `"maximum number of steps"` 和 `MAX_STEPS = 10` 的词集交集只有一个 `steps`,
> 而 `"cloned repositories"` 和 `REPOS_DIR` **交集是空的**。
> BM25 没有词形归一化就跨不过去,而 embedding 训练时学过 `max ≈ maximum`。
>
> 所以结论我限定在:**没做词形归一化的 BM25,在代码语料上没有互补价值。**
> 要真用起来,得先补 stemming 和缩写展开。

这段话里有三样面试官在找的东西:**先量再做的顺序、可归因的数字、以及主动收窄的结论边界**。

路线里那个「一个你主动放弃的方案」的故事,这段就是。
