## 背景:两个公式

这一节是你需要的**外部知识**,不是要你抄的实现。

### BM25

给定查询 Q 和文档 D:

```
score(D, Q) = Σ  IDF(q) · f(q,D)·(k1+1) / ( f(q,D) + k1·(1 - b + b·|D|/avgdl) )
             q∈Q
```

- `f(q,D)`:词 q 在文档 D 里出现几次(词频 TF)
- `|D|`:文档长度(token 数);`avgdl`:全部文档的平均长度
- `IDF(q) = ln(1 + (N - n(q) + 0.5) / (n(q) + 0.5))`,`n(q)` 是含 q 的文档数

两个参数各控制什么 —— **这是必考点**:

| 参数 | 控制什么 | 极端值会怎样 |
|--|--|--|
| `k1` | 词频饱和速度 | `k1=0` 时词频完全不起作用,只剩 IDF |
| `b` | 文档长度归一化强度 | `b=0` 时完全不管长度,长文档天然占便宜 |

常用 `k1=1.5`、`b=0.75`。**用默认值就要说出来是默认值** —— 否则面试官会追问你是怎么调的。

### RRF(Reciprocal Rank Fusion)

```
score(d) = Σ  w_i / (k + rank_i(d))          k 通常取 60
           i
```

`rank_i(d)` 是文档 d 在第 i 个检索器结果里的**排名**(1 开始),没出现就不计这一项。

**为什么融合排名而不是分数**:余弦距离和 BM25 分数量纲完全不同,
要相加就得先归一化,而归一化方式本身会变成一个隐藏的调参旋钮 ——
**那个旋钮会悄悄替你做真正的决策**。用排名就绕开了这件事。

**代价**:RRF **奖励一致性**。两个检索器都找到的文档白拿一份加分,
只被一个检索器找到的文档会被系统性压制,**不管那个检索器多确信**。
记住这条,第三步会用到。

### 任务 B:BM25 索引(约 60 行)

一个类,构造时接收 `(ids, documents)`,提供 `search(query, n) -> [(doc_id, score)]`。

构造时要预计算:每篇文档的词频表、每篇长度、平均长度、每个词的文档频率。

**注意上面 IDF 公式里那个 `1 +` 是干什么的**:

经典 Robertson IDF 是 `ln((N - n + 0.5) / (n + 0.5))`,**没有 `1 +`**。
当一个词出现在超过一半文档里时,括号内小于 1,取对数就是**负数** ——
负分意味着「含有这个词反而扣分」,这通常不是你想要的。

加上 `1 +` 之后,下界变成 `ln(1) = 0`,**自然不会为负**。
自己验一下:把 `n = N`(所有文档都含这个词)代进去,等于多少?

> 我的 `hybrid.py` 里在平滑版之外还写了一层 `max(idf, 0.0)` —— **那是冗余的**,
> 用这个公式它永远不会触发。你重写时可以不写,但要说得出为什么不用写。

验收:

```python
# 213 篇文档,查一个明确的标识符,正确的块应该排第 1
hits = index.search("what is the value of BLOCKED_COMMANDS", 5)
# 中文查询应该返回空
assert index.search("向量检索默认返回几条结果", 5) == []
```

文档从哪来?**直接从 Chroma 取回**,不要重新调 `chunk_repository()`:

```python
collection = store.client.get_collection(collection_name)
got = collection.get(include=["documents", "metadatas"])
```

为什么:如果切块器改过而索引没重建,两条路会搜到**不同的语料**,
你就会得到一个无法归因的结果。**从索引里取,两个检索臂一定搜的是同一批文本。**

### 任务 C:RRF 融合(约 20 行)

输入两个 id 列表和两个权重,输出融合后的 id 列表。

验收 —— **这条测试比前面两个都重要**:

```python
# A 只被向量找到, 而且是 rank 1
# B 被两个检索器都找到, 但都只排 rank 10
vector_ids = ["A", "p1", "p2", "p3", "p4", "p5", "p6", "p7", "p8", "B"]
bm25_ids   = ["q1", "q2", "q3", "q4", "q5", "q6", "q7", "q8", "q9", "B"]

out = fuse(vector_ids, bm25_ids, 1.0, 1.0)

# A = 1/(60+1)              ≈ 0.0164
# B = 1/(60+10) + 1/(60+10) ≈ 0.0286
assert out[0] == "B"
```

**如果你的实现让 B 赢了,不是你写错了 —— 这就是 RRF 的设计。**
把这个数字算明白,你就懂了第三步为什么会翻车。

## 第三步:自己做实验(约 1.5 小时)

**这一步别看我的结论。** 顺序很重要:

### 3.1 先分开测两个臂 ← 从这里开始

在跑任何融合之前,先让 BM25 **单独**跑一遍评测,和纯向量对比,按类别列表。

```
类别                 向量单独    BM25单独
exact_identifier      ____%      ____%
semantic              ____%      ____%
value_lookup          ____%      ____%
cross_file            ____%      ____%
```

填完这张表再往下。**这五分钟的检查决定了后面要不要做融合。**

> **规则:如果一个臂在所有类别上都被另一个臂支配,融合不可能有增益,只能有稀释。**
> 融合的前提是**互补** —— A 在某类上赢 B,B 在另一类上赢 A。
> 没有互补就没有可融合的东西,**这时候调权重是在给噪声调音量**。
>
> 我把顺序做反了:直接实现融合就跑,一个类别掉了 36 个点,排查了一整轮才回头做这张表。

### 3.2 写预测,再跑参数扫描

**动手前想清楚一件事:哪些类别不该动?**

这次有个现成的**自检项**:中文 `semantic` 是纯自然语言,BM25 切不出 token,
**它在机制上就不该动**。如果它大幅变了,先查你的实现,别当成发现。

比「预期涨多少」更有用的是「预期什么不变」——后者能帮你区分
「改动生效了」和「我把公共代码改坏了」。

然后扫参数。建议 `CANDIDATE_K ∈ {10, 20, 50}` × `W_BM25 ∈ {0.3, 0.5, 1.0}`。

⚡ **效率提示**:别跑 9 次 `run_eval.py`。embedding 和 BM25 检索**只算一次**缓存起来,
换参数只是重新排序,几乎免费。9 组能在一次进程里跑完。

### 3.3 结果不对时,先分清是哪种「不对」

你大概率会看到某一类掉得特别狠。这时候要判断:

| 现象 | 更可能是 |
|--|--|
| 单一类别暴跌、其余不动 | **实现 bug 或参数错**,先查 |
| 各类别普遍小幅下降 | 方向问题 |

查的方法:**逐条列出正确块在「向量单独 / BM25单独 / 融合后」三处的排名**。
如果看到「向量 rank 1 → 融合后 rank 12」,回去看第二步任务 C 那个验收测试。

**参数问题和方向问题必须分开。** 参数错会让结果更差,但参数对了也救不回一个错的方向 ——
不区分的话,你会在错的方向上一直调下去。

> 要真用起来,得先补 stemming 和缩写展开。

> ⚠️ **先自己试过再看。** 上面每道题都给了「怎么自己验」,

> 下面每条答案都是**实际跑出来的**,不是推理。除非特别说明,
> 表格都是 **BM25 单独检索、英文查询、@5**——单独测比测融合干净,
> 因为融合会把两个臂的效应混在一起。

<details>
<summary><b>Q1 · b=0 会发生什么</b></summary>

`b` 控制**文档长度归一化强度**:`norm = 1 - b + b·(|D|/avgdl)`。
`b=0` 时 `norm` 恒为 1,**完全不管长度**——长文档因为词出现次数多,天然占便宜。

| 设置 | exact | semantic | value | cross_file |
|--|--:|--:|--:|--:|
| **默认 k1=1.5 b=0.75** | **93%** | 56% | 36% | **27%** |
| b=0(不归一) | 80% | 56% | 36% | 13% |
| b=1(完全归一) | 80% | 56% | **43%** | 27% |

变化最大的是 `exact_identifier`(-13)和 `cross_file`(-14)。
它们的目标是短小聚焦的函数定义(`def check_command(` 所在的块才 509 字符),
不做归一就被「碰巧含这个词的长文档」挤掉。

反过来 `b=1` 让 `value_lookup` +7,因为那一类的目标是 `OVERLAP = 10` 这种十几字符的小块。

> **两个极端都让 `exact` 掉 13** —— 说明 0.75 在这个语料上确实接近最优,不是随手填的。
> 面试被问「你调过参数吗」,这张表就是答案。

</details>

<details>
<summary><b>Q2 · k1=0 呢</b></summary>

代进公式:`f·(k1+1) / (f + k1·norm)` 在 `k1=0` 时 = `f·1/f` = **1**(只要 f>0)。

**BM25 退化成 `Σ IDF(q)`** —— 词频完全不起作用,只剩「查询词出没出现」×「稀有度」,
也就是**一个 IDF 加权的布尔匹配**。长度归一化也一并失效(`k1·norm` 里的 0 把它抹掉了)。

| 设置 | exact | semantic | value | cross_file |
|--|--:|--:|--:|--:|
| 默认 | 93% | 56% | 36% | 27% |
| **k1=0** | 93% | **62%** | 36% | **13%** |

`semantic` 反而 **+6**,因为重复不再加分。

对照实验里有个现成的例子:查询「which tool groups does the navigator register」时,
BM25 的 top-5 全被 `README.md` 占了——就因为 README 里 "tool" 出现次数远多于代码块。
**关掉词频,这种「刷词数」的优势就没了。**

</details>

<details>
<summary><b>Q3 · 为什么 RRF 用排名不用分数</b></summary>

真写了两版归一化融合来对比。**同样两个检索器、同样权重,只换归一化方式**:

| 融合方式 | exact | semantic | value | cross | **整体** |
|--|--:|--:|--:|--:|--:|
| RRF(排名) | 100% | 81% | 43% | 30% | **64%** |
| min-max 归一 | 100% | 75% | 64% | 32% | **68%** |
| z-score 归一 | 100% | 75% | 64% | 39% | **70%** |

**6 个百分点的差距,完全来自「你选了哪种归一化」。**
那个选择做的工作量,和检索器本身一个量级。
RRF 用排名,就是为了**把这个隐藏旋钮从系统里拿掉**。

⚠️ 但要诚实:这里归一化版**赢了** RRF(70% vs 64%)。
所以正确的说法不是「RRF 更好」,而是
**「RRF 更少一个你说不清楚的自由度」**。

而且三种融合**全都输给纯向量的 76%** —— 融合方式怎么选都救不回没有互补性的方案。

</details>

<details>
<summary><b>Q4 · CANDIDATE_K=50 在 213 篇上为什么错</b></summary>

```
语料 213,每臂取 50        →  占 23.5%
随机独立时的期望重叠       →  50×50/213 = 11.7 篇
实测平均重叠              →  23.9 篇(中位 24,最大 42)
```

实测重叠是随机期望的**两倍**——因为两个检索器本来就相关,都在找相关文档。

结果:融合池里大约 76 个候选,**其中 24 个拿到了「一致性加分」**。
RRF 设计里这个加分本该是**罕见而强的信号**,当三分之一候选都有它时,它就变成噪声了。

百万级语料同样取 50:期望重叠 = 50×50/10⁶ = **0.0025 篇**,几乎必然为 0。
那时两边都命中才是真信号——**RRF 正是为这个场景设计的**。

> 所以答案是:**不是 `CANDIDATE_K=50` 绝对错,是 50 相对 213 太大。**
> 换成百万级语料,同样的参数就对了。

</details>

<details>
<summary><b>Q5 · BM25 为什么在 exact 强、在 value_lookup 弱</b></summary>

先测交集**大小**,讲不通——有条失败查询的交集有 6 个词。
改测**交集里最稀有那个词的 IDF**,答案立刻出来:

| 类别 | 查询 | \|∩\| | **max IDF** | 最稀有的词 |
|--|--|--:|--:|--|
| exact | where is check_command defined | 4 | **4.45** | `check_command` |
| exact | execute_grep function | 3 | **4.45** | `execute_grep` |
| exact | MemoryStore class | 4 | **3.66** | `memorystore` |
| value | which embedding model is used | 1 | **1.21** | `model` |
| value | what is the default model identifier | 1 | **1.21** | `model` |
| value | where are cloned repositories stored | **0** | **0.00** | — |

> **关键不是交集大小,是交集里有没有稀有词。**

`exact_identifier` 的查询**字面写出了标识符**,`check_command` 的 IDF 是 4.45,
全语料几乎只有一处,一击必中。
`value_lookup` 是自然语言描述,交集只剩 `model` 这种 IDF 1.21 的大众词,甚至是**空集**。

**这也是一次「差点用错指标」的记录**:交集大小是个看起来合理、实际讲不通的量。
换成 IDF 之后规律才浮出来。**指标选错,再干净的数据也读不出东西。**

</details>

<details>
<summary><b>Q6 · 分词器为什么要保留两个粒度</b></summary>

| 分词方式 | exact | semantic | value | cross_file |
|--|--:|--:|--:|--:|
| **两个粒度都留** | **93%** | **56%** | 36% | **27%** |
| 只留整体标识符 | 87% | 50% | 36% | **17%** |
| 只留子词 | **80%** | 56% | 36% | 27% |

- **只留整体** → `cross_file` 掉 10 分。查询写 "tool groups" 永远匹配不上 `FILE_TOOLS`
- **只留子词** → `exact_identifier` 掉 13 分。`execute_grep` 被拆成 `execute`+`grep`
  两个大众词(回想 Q5:精度全在那个高 IDF 的整体标识符上)

**两个粒度在每个类别上都不劣于任一单粒度。**
这是少数几个「两个都要」真的正确的场合——多数时候「都要」是没想清楚。

</details>

<details>
<summary><b>Q7 · 要救这个方案,第一步做什么</b></summary>

**补词形归一化。** 证据直接来自 Q5 最后一行:

```
"where are cloned repositories stored"  ∩  "REPOS_DIR = Path"  =  空集
```

`repositories` 和 `repos` 是同一个东西,BM25 看不出来。
加 stemmer(Porter / Snowball)或缩写词典
(`repos↔repositories`、`max↔maximum`、`config↔configuration`),这个交集就非空了。

**做完这一步再谈混合检索值不值得。**
现在测到的是「**没做词形归一化的 BM25**」,结论的作用范围就只到这里为止——
把它说成「混合检索在代码上没用」就超范围了。

</details>

## 这些数字怎么来的

全部用仓库里现成的东西跑出来的,可复现:

- BM25 参数变体:monkeypatch `hybrid.K1` / `hybrid.B`,重建 `BM25Index`
- 分词器变体:monkeypatch `hybrid.tokenize`
- 归一化融合:另写 min-max / z-score 两版对照 `fuse`
- 重叠统计:对 60 条英文查询取两臂 top-50 求交集

**embedding 只算一次全程复用** —— 换参数只是重新排序,9 组变体在一个进程里跑完,
比跑 9 次 `run_eval.py` 快一个量级。做参数扫描时值得这么写。
